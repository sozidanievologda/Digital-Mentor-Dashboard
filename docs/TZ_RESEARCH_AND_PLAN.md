## 3. Исследование API (факты, не предположения)

### 3.1. Эндпоинты

| Метод | Что делает | Ограничения |
|---|---|---|
| `POST /v1/company/auth/getToken` | `{apiKey}` → `{accessToken, expiresAt, level}` | Токен живёт ~7 дней, можно кэшировать |
| `GET /v1/company/users?limit&offset` | `{users: [...], stats: {totalItems}}` | `limit` **максимум 500** (1000 → `RequestValidationError`); фильтры по тегам игнорируются |
| `GET /v1/company/managers` | Плоский массив | `limit/offset` игнорируются, всегда 198 записей |
| `GET /v1/company/userTags` | Справочник всех тегов компании | Возвращает весь список |
| `GET /v1/company/classes` | Список занятий/курсов | Для будущей аналитики |

### 3.2. Поля пользователя

```
id, name, phone, email, createdAt, updatedAt, enabled,
tags: [{id, name}], attributes: [{attributeName, attributeType, value}],
joins: [{classId, statusId, createdAt, tags: [tagId, ...]}],
filials, stateChangedAt, clientStateId, createSourceId, ...
```

### 3.3. Главное открытие: текущая метрика неверна

- В CRM **3519** пользователей, но только **736 уникальных** имеют хотя бы один тег проекта `ФПГ_ЦН`.
- То есть дашборд показывает 3519 вместо ~736 — завышение в 4,8 раза.
- Теги проекта: **19 различных** названий с префиксом `ФПГ_ЦН` (в ТЗ перечислен 21 — список меняется, его нельзя хардкодить).
- Самая массовая активность: «Консультации Цифровой наставник» — 546 человек; далее мастер-классы по 5–82 человека.
- Серверная фильтрация `?tags=`, `?tagId=`, `?tagIds=`, `?filters=` **не работает**: `stats.totalItems` остаётся 3519. Фильтровать нужно на бэкенде после выгрузки.

### 3.4. История участия

- Даты назначения тегов API не отдаёт (эндпоинты `/users/tags`, `/users/{id}/tags` возвращают ошибки валидации).
- `createdAt` — дата создания карточки в CRM, а не начала участия: у **174 из 736** участников карточка создана раньше старта проекта (до февраля 2025), у 562 — позже.
- Значит, строить историю по `createdAt` или `lastLogin` (как сейчас) некорректно.

### 3.5. Надёжность и лимиты

- Периодически наблюдаются обрывы соединения (`ConnectionResetError`) при выгрузке — нужны ретраи с backoff.
- Rate limit в документации не описан; параллелизм ограничен 4 воркерами.
- Формат ошибок: `{"code": "RequestValidationError", "message": "..."}`, `{"code": "NotFound"}`.

## 5. Целевая архитектура

```
CRM «МойКласс»
   │  (раз в час + по кнопке «Обновить»)
   ▼
Collector (FastAPI background scheduler)
   │  users (limit 500, parallel) → фильтр по тегам ФПГ_ЦН → дедуп
   ▼
SQLite
   ├── users(id, created_at, updated_at, raw_json, fetched_at)
   ├── tags(id, name)
   ├── user_tags(user_id, tag_id)
   └── snapshots(taken_at, project_users, total_users, volunteers)
   ▼
API (читает SQLite, отвечает мгновенно)
   ├── GET /api/dashboard/metrics   → live/stale/error + last_success_at
   └── GET /api/dashboard/history   → из snapshots (7/30/all/custom)
   ▼
Frontend (nginx, Chart.js, session-cookie auth)
```

Ключевые принципы:
- Браузер никогда не обращается к CRM.
- Последний успешный снимок всегда доступен, даже если CRM лежит.
- История — из собственных снапшотов, а не из `createdAt`.
- Фильтр проекта — конфигурируемый префикс/список тегов, а не хардкод.

Схема данных (минимум):

```sql
users(id INTEGER PRIMARY KEY, created_at TEXT, updated_at TEXT, raw_json TEXT, fetched_at TEXT)
tags(id INTEGER PRIMARY KEY, name TEXT)
user_tags(user_id INTEGER, tag_id INTEGER, PRIMARY KEY (user_id, tag_id))
snapshots(taken_at TEXT PRIMARY KEY, project_users INTEGER, total_users INTEGER, volunteers INTEGER)
```

## 8. Риски, допущения и вопросы заказчику

1. **Что считать «получил помощь»?** Любой тег `ФПГ_ЦН`? Включать ли «Вебинары для библиотек» (библиотекари, не пенсионеры)? Сейчас оценка — 736 уникальных; нужно письменное подтверждение методики.
2. **Дата участия.** CRM не отдаёт дату назначения тега. Предлагаем снапшоты с момента внедрения; бэкфилл по датам в названиях тегов — только как оценочный и с пометкой.
3. **Волонтёры.** В ТЗ ключевая метрика — только пенсионеры. Оставляем волонтёров как второстепенный показатель?
4. **Экспорт.** CSV достаточно, или нужен Excel/PDF/скриншот?
5. **Доступы.** Сколько пользователей, нужен ли SSO/интеграция с чем-то, требования к паролям?
6. **Хостинг.** Где разворачиваем (сервер заказчика, облако), есть ли домен и TLS?
7. **Приватность.** На дашборде только агрегаты; персональные данные не выводим и не логируем.

### Безопасность (срочно)

- В приложении к PDF открытым текстом указаны логин и пароль к CRM. Считайте их **скомпрометированными**: смените пароль, не храните учётные данные в документах, доступ к PDF ограничьте.
- API-ключ, который ранее был в git, тоже подлежит перевыпуску (он остаётся в истории коммитов).
- CORS `*` нужно заменить на список origin после внедрения авторизации.
