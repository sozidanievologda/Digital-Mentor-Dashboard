Установка и запуск

Предварительные требования

- Python 3.11+ (желательно в virtualenv)
- Docker + Compose v2 (опционально)

Запуск через Docker (рекомендовано)

1. Создайте `backend/.env` по шаблону `backend/.env.example` и укажите `MOYKLASS_API_KEY`.
2. Из корня репозитория выполните:

       docker compose up -d --build

3. Откройте `http://localhost:8080` (Swagger — `http://localhost:8080/docs`).

Контейнер `frontend` (nginx) раздаёт статику и проксирует `/api/` в `backend`, поэтому фронтенд обращается к API по относительному пути.

Запуск бэкенда (локально, рекомендовано для разработки)

1. Перейдите в папку `backend`:

       cd backend

2. Запустите приложение Uvicorn:

       python -m uvicorn app.main:app --host 0.0.0.0 --port 8000

После старта сервер будет доступен по адресу `http://localhost:8000`.

Фронтенд

Откройте файл `frontend/index.html` в вашем браузере (file://) и он будет обращаться к бэкенду по `http://localhost:8000`. Либо используйте Docker-запуск выше.


Бэкенд


Структура и важные изменения :

- `backend/app/utils/config.py` — конфигурация API. Ключ и адреса эндпоинтов читаются из переменных окружения (`backend/.env`, шаблон — `backend/.env.example`).
- `backend/app/services/crm_service.py` — работа с API "МойКласс" (аутентификация, пагинация).
- `backend/app/services/data_processing.py` — обработка и построение метрик/истории.
- `backend/app/api/dashboard_data.py` — роуты REST API.

Ключевые моменты реализации

1) Аутентификация и запросы к CRM

- `get_token_api()` авторизуется по `URL_AUTH`, кэширует `accessToken` до `expiresAt` и переиспользует его между запросами.
- `fetch_all_users()` и `fetch_all_managers()` используют общий загрузчик `_fetch_all_pages()`: страницы по 500 записей (максимум, который принимает API), общее число страниц берётся из `stats.totalItems`, остальные страницы запрашиваются параллельно (4 воркера).
- Записи дедуплицируются по `id`. Защита от «залипшей» пагинации: если страница не приносит новых записей (так ведёт себя `/managers`, игнорирующий `offset`), загрузка останавливается с предупреждением в логе.
- Защита от бесконечной пагинации: `MAX_PAGES = 100`; если лимит реально достигнут, в лог пишется warning о возможной неполноте данных.

2) Кэширование и производительность

- В `data_processing.py` хранится один общий in-memory снимок данных CRM (пенсионеры + волонтёры); и метрики, и история считаются из него, поэтому загрузка дашборда обращается к CRM один раз, а не дважды.
- Пенсионеры и волонтёры загружаются параллельно; одновременные запросы `/metrics` и `/history` не создают повторную выгрузку.
- `CACHE_TTL_SECONDS` (по умолчанию 300) задаёт время жизни снимка. После истечения TTL отдаётся прежний снимок, а обновление выполняется в фоне (stale-while-revalidate): после первого прогрева ответы приходят мгновенно.

3) Построение историй

- `_extract_item_date(item)` ищет дату в приоритетных полях (`lastLogin`, `lastActive`, `lastUpdate`, `updatedAt`, затем поля создания `createdAt`, `created_at` и т.д.) и возвращает `datetime.date`.
- `_build_history_from_items(items, days)` собирает количество пользователей по датам и строит кумулятивную временную серию на `days` дней.
- По умолчанию история строится из реальных дат, если они доступны.

4) Логи и отладочная информация

- Добавлены дополнительные логи: количество полученных записей, первые ключи записи, а также счётчики активных/неактивных (`enabled`) элементов — это помогает сверять данные с отчётами CRM.

API эндпоинты

GET /api/dashboard/metrics
- Описание: Возвращает текущие метрики
- Ответ:

      {
            "pensioners_count": 3315,
            "volunteers_count": 9750,
            "last_updated": "2026-06-02T07:30:00",
            "status": "active"
      }

GET /api/dashboard/history?period={period}
- Параметры: `period` — `7d`, `30d`, `90d`, `all` (для `all` по умолчанию берётся ~365 дней)
- Описание: Возвращает временные ряды для `pensioners` и `volunteers` в формате массива объектов `{date, count}`.

Примеры ответа:

      {
            "period": "30d",
            "pensioners": [{"date":"2026-05-04","count":12}, ...],
            "volunteers": [{"date":"2026-05-04","count":50}, ...]
      }


Фронтенд


- `frontend/js/api_client.js` — axios-клиент для `/api/dashboard/metrics` и `/api/dashboard/history`.
- `frontend/js/main.js` — рендер графика через Chart.js, управление кнопками периода и обновлением метрик.


Про наблюдаемую проблему: пачки волонтёров в графике

Описание проблемы

При визуализации истории волонтёров на графике обнаружены резкие скачки (порой сотни или тысячи человек за один день), а также частые небольшие пачки по ~50 человек. Эти скачки воспроизводятся в данных, полученных от API — бэкенд не аггрегирует и не сглаживает такие загрузки, он отображает то, что вернул CRM.

Что показали логи

- Примеры найденных дат и партий:
      - 2023-03-24: 1850 волонтеров
      - 2024-02-10: 1250 волонтеров
      - 2021-12-21: 1050 волонтеров
      - 2026-05-18: 600 волонтеров
      - Множество дат с партиями 50/100/150/200 и т.д.

Возможные причины (теории)

1) Импорт из файла (Excel/CSV)
       - Частая причина массового внесения сотрудников/волонтёров — пакетный импорт из таблицы.

2) Миграция/синхронизация из другой системы
       - Данные могли быть перенесены оптом из старой БД или внешней системы в один момент.

3) Автоматизированная регистрация/онбординг
       - Скрипты или интеграции, автоматически создающие аккаунты партиями.

4) Дубликаты/массовое объединение
       - Результат операций по массовому объединению/восстановлению записей.

5) Ручной ввод из админки с групповыми операциями
       - Администраторы могут создавать несколько записей одновременно.

6) Ошибка в источнике данных
       - Некорректная агрегация в CRM-отчёте или дублирование, если несколько сущностей представлены как отдельные записи.
