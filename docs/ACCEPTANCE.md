# Приёмка по ТЗ

Документ фиксирует методику расчёта и порядок проверки требований ТЗ (раздел 7).

## 1. Методика расчёта ключевой метрики

**«Пенсионер, получивший помощь»** — уникальный пользователь CRM, у которого есть хотя бы один тег проекта с префиксом `ФПГ_ЦН` (или тег из `PROJECT_TAG_NAMES`, если задан точный список).

- Счёт идёт по уникальным `user.id`: несколько тегов у одного человека не задваивают число.
- В метрику **не** входят все остальные пользователи CRM (контакты вне проекта).
- Волонтёры (`/v1/company/managers`) считаются отдельно и не входят в key metric.
- Список тегов не хардкодится: новые активности с префиксом `ФПГ_ЦН` попадают в расчёт автоматически.

Контрольные значения на 17.11.2026:

| Показатель | Значение |
|---|---|
| Всего пользователей CRM | 3519 |
| Уникальных участников проекта | **736** |
| Тегов проекта | 19 |
| Волонтёров | 198 |

### Открытый вопрос к заказчику

Тег `ФПГ_ЦН Вебинары для библиотек Цифровой наставник` относится к библиотекарям, а не к пенсионерам (3 пользователя). Нужно решить, включать ли его в метрику. Если нет — задайте точный список:

```ini
PROJECT_TAG_NAMES=ФПГ_ЦН Консультации...,ФПГ_ЦН Мастер-класс по ИИ,...
```

## 2. Сверка с CRM

```bash
cd backend
python scripts/verify_metrics.py --details
```

Скрипт выгружает данные из CRM, считает участников тем же алгоритмом и сравнивает с последним снимком дашборда:

```
CRM «МойКласс»:
  участников проекта: 736
  всего пользователей: 3519
  волонтёров: 198
Последний снимок дашборда:
  ...
РЕЗУЛЬТАТ: OK — данные дашборда совпадают с CRM.
```

Код возврата: `0` — совпало, `1` — расхождение, `2` — ошибка. Перед сверкой нажмите «Обновить» в дашборде, чтобы снимок был актуальным.

## 3. Проверка истории

- Последняя точка графика должна совпадать с ключевой метрикой.
- Дни до первого запуска помечаются `approximate: true` и рассчитываются по датам создания карточек (CRM не отдаёт дату назначения тега). Это ограничение зафиксировано в интерфейсе.
- После накопления ежедневных снапшотов история становится фактической.

## 4. Проверка производительности и безопасности

| Проверка | Команда/действие | Ожидание |
|---|---|---|
| Загрузка API | `curl -w '%{time_total}' -H 'Authorization: Bearer …' https://…/api/dashboard/metrics` | < 3 с |
| Защита API | `curl -i https://…/api/dashboard/metrics` | 401 |
| Вход | неверный пароль | 401; после 10 попыток — 429 |
| Статус | `/api/health` | `data_status: live` |
| HTTPS | `curl -I https://…` | 200 + HSTS |
| CORS | запрос с чужого Origin | нет `Access-Control-Allow-Origin` |
| Секреты | `git grep` по репозиторию | ключей и паролей нет |
